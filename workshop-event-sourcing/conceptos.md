Event Sourcing ≠ cola en memoria
<div class="text-2xl opacity-80 font-light mt-2"> ES, <span class="text-teal-400">Domain Events</span> y <span class="text-amber-400">EDA</span> no son lo mismo — y no deben compartir el mismo mecanismo. </div> <div class="abs-br m-6 cite"> Postura del equipo · fundamentada con Fowler, Vernon, Bogard, Khorikov, CodeOpinion </div> <!-- Objetivo: alinear al equipo sobre por qué el mecanismo actual (eventos privados → cola en memoria → handler inmediato) mezcla tres patrones distintos, y proponer una regla clara para el building block. No es un ataque al patrón de domain events: es acotar dónde aplica cada cosa. -->
layout: two-cols
Lo que observamos hoy
Un comando produce eventos privados, que se publican en una cola en memoria y son handleados inmediatamente por otro handler que ejecuta más lógica de dominio.

<div class="panel mt-4"> <span class="text-red-400 font-mono">Síntoma:</span> el <code>ITenantResolver</code> pierde el contexto y no puede levantar los datos. </div> <div class="mt-4 opacity-70 text-sm"> El bug del tenant <b>no es la causa</b>. Es el detector de humo de un problema conceptual. </div>
::right::

layout: statement
Nuestra postura
No prohibimos combinar ES y EDA.<br/> Prohibimos el mecanismo ambiguo que mete bajo un mismo<br/> "evento → cola en memoria → handler" tres cosas distintas.

<div class="mt-6 text-base opacity-70">La pregunta concreta: ¿soportamos que un mismo comando/transacción se desglose en varios handlers vía una cola en memoria? Lo ponemos bajo la lupa <b>caso por caso</b>, dándole a cada uno su mecanismo.</div>
ES y EDA resuelven problemas distintos
<div class="grid grid-cols-2 gap-6 mt-4"> <div class="panel"> <div class="text-teal-400 font-mono text-sm">EVENT SOURCING</div> <div class="text-xl font-semibold mt-1">Persistencia</div> <p class="opacity-80 mt-2">Los eventos <b>son el estado</b>. Hechos inmutables que se almacenan secuencialmente; el estado actual se <b>reconstruye</b> reproduciéndolos.</p> </div> <div class="panel"> <div class="text-amber-400 font-mono text-sm">EVENT-DRIVEN ARCHITECTURE</div> <div class="text-xl font-semibold mt-1">Comunicación</div> <p class="opacity-80 mt-2">Los eventos sirven para <b>comunicar entre límites</b> de servicio, desacoplando emisor y receptor de forma asíncrona.</p> </div> </div> <div class="mt-6 cite"> Derek Comartin (CodeOpinion): ES = usar eventos como estado · EDA = usar eventos para comunicar entre boundaries.<br/> Rafael Andrade / Estuary: "no son alternativas; muchos sistemas usan ambos, pero para cosas diferentes". </div> <!-- Punto de anclaje. Ambos giran en torno a "eventos", de ahí la confusión, pero el propósito, el scope y los atributos son distintos. -->
El evento de ES es estado — handlearlo ya es EDA
<div class="text-lg mt-2">El "sourcing" significa que tu estado se <span class="text-teal-400">reconstruye a partir de</span> (is <i>sourced from</i>) el log de eventos. Sí, el comando emite eventos — el matiz es <b>en qué rol</b> los usás.</div> <div class="grid grid-cols-2 gap-6 mt-6"> <div class="panel"> <div class="text-teal-400 font-mono text-sm">ROL ES · estado</div> <p class="opacity-85 mt-2">El evento es un <b>hecho persistido que define el estado</b>. Vive en el event store y se reproduce para reconstruir el agregado.</p> </div> <div class="panel"> <div class="text-amber-400 font-mono text-sm">ROL EDA · mensaje</div> <p class="opacity-85 mt-2">Sí, un evento <b>puede</b> ser un mensaje para handlear. Pero publicarlo para que otro handler reaccione <b>ya es EDA</b>.</p> </div> </div> <div class="mt-5 panel border-red-500"> <span class="text-red-400 font-mono text-sm">El error:</span> handlearlo <b>fingiendo que sigue siendo ES/in-process</b> — saltándose lo que EDA exige: async, durabilidad, idempotencia, consistencia eventual y <b>contexto en el payload</b>. </div>
Están confundiendo patrones distintos
<div class="opacity-70 text-sm font-mono">Martin Fowler — "The Many Meanings of Event-Driven Architecture" (GOTO 2017)</div> <div class="grid grid-cols-2 gap-4 mt-4"> <div class="panel"><b>1. Event Notification</b><br/><span class="opacity-75 text-sm">Avisar a otros de un cambio. Sin esperar respuesta.</span></div> <div class="panel"><b>2. Event-carried State Transfer</b><br/><span class="opacity-75 text-sm">El evento lleva los datos para no volver al origen.</span></div> <div class="panel"><b>3. Event Sourcing</b><br/><span class="opacity-75 text-sm">El log de eventos es el registro primario del estado.</span></div> <div class="panel"><b>4. CQRS</b><br/><span class="opacity-75 text-sm">Separar el modelo de escritura del de lectura.</span></div> </div> <div class="mt-5 panel border-amber-500"> <span class="text-amber-400 font-mono text-sm">El lado oscuro de EDA:</span> ganas desacoplamiento, pero pierdes la capacidad de <b>entender qué pasa siguiendo el código paso a paso</b>. No hay una vista del comportamiento global. </div>
layout: center
El olor real: Evento vs Comando
<div class="grid grid-cols-2 gap-8 mt-4 max-w-4xl"> <div class="panel"> <div class="text-teal-400 font-mono">EVENTO</div> <p class="mt-2 opacity-85">Hecho en pasado · inmutable · el emisor <b>no espera respuesta</b> ni controla la reacción.</p> </div> <div class="panel"> <div class="text-amber-400 font-mono">COMANDO</div> <p class="mt-2 opacity-85">Intención imperativa · dirigida · <b>puede ser rechazada</b> · esperas un efecto concreto.</p> </div> </div> <div class="mt-6 text-lg max-w-4xl"> Si un handler "reacciona" a un evento ejecutando <b>lógica de dominio que cambia estado y puede fallar</b>, eso no es reaccionar a un hecho: es un <span class="text-red-400">comando disfrazado de evento</span>. </div> <div class="mt-4 cite"> Vladimir Khorikov (Enterprise Craftsmanship): usa domain events para comunicación entre aplicaciones / efectos más allá de la BD. Para flujo <i>dentro</i> de la app, deja el flujo explícito: devuelve el resultado y pásalo al siguiente método. </div>
El patrón in-process SÍ existe — y es legítimo
<div class="opacity-80">Levantar domain events y despacharlos in-process es un patrón <b>legítimo y respetado</b>:</div> <div class="mt-4 space-y-3"> <div class="panel"><b>Jimmy Bogard</b> — <i>A better domain events pattern</i>: no despaches al instante; <b>registra</b> los eventos y despáchalos justo antes/después del commit.</div> <div class="panel"><b>Microsoft</b> — guía de microservicios .NET + eShopOnContainers (MediatR) lo adoptan como referencia.</div> <div class="panel"><b>Udi Dahan / Khorikov</b> — variantes "dispatch antes vs después del commit".</div> </div> <div class="mt-5 panel border-amber-500"> <span class="text-amber-400 font-mono text-sm">La diferencia crítica:</span> esos patrones despachan en un <b>punto controlado</b> y en el <b>mismo contexto/transacción lógica</b> — no "una cola en memoria handleada inmediatamente" en otro scope. </div> <div class="mt-3 cite"> Microsoft (<i>Domain events: design & implementation</i>): para domain events «<b>real messaging would be overkill</b>… you just need to process those events within the same process». El broker es para integration events, no para esto. </div>
La regla que decide cada caso
<div class="text-lg">Evans/Vernon: <span class="text-teal-400">1 transacción = 1 agregado</span> — es un <b>rule of thumb</b>, no una ley.</div> <div class="panel mt-4 border-teal-500"> <span class="font-mono text-sm">Criterio de Vernon:</span> ¿es <b>trabajo del usuario que ejecuta el caso de uso</b> dejar los datos consistentes? → <b>transaccional</b>. ¿Es trabajo de <b>otro usuario o del sistema</b>? → <b>consistencia eventual</b>, en transacción separada. </div> <p class="opacity-85 mt-3"> Tu <code>IPrivateEvent</code> <b>afecta a otro agregado</b>: por defecto eso pide <b>consistencia eventual</b> (otra transacción). Solo va en la misma transacción si es efecto acotado <b>del mismo comando</b> (matiz de Bogard) — y entonces in-process pre-commit, <b>no por cola</b>. </p> <div class="mt-4 cite"> Vaughn Vernon, <i>Effective Aggregate Design, Part II</i>: «one aggregate per transaction is a <b>rule of thumb</b>». Eric Evans, <i>DDD</i> (p.128): las reglas que cruzan agregados no se esperan consistentes en todo momento. </div>
El problema técnico real: local:// no es durable
<div class="opacity-80">En Wolverine/Marten (CritterStack), una cola <code>local://</code> es <b>in-memory</b> (TPL Dataflow), en proceso, y <b>no durable por defecto</b>.</div> <div class="mt-4 panel border-red-500"> <span class="text-red-400 font-mono text-sm">Docs de Wolverine:</span> «messages in the in-memory queues <b>can be lost</b> in the case of the application shutting down unexpectedly… you will need to use <b>Durable endpoints</b> to take advantage of the persistent outbox». </div> <div class="mt-4 grid grid-cols-2 gap-4"> <div class="panel"><b>Corre en otra transacción</b><br/><span class="opacity-75 text-sm">El "mismo transaction" que se cree tener entre el comando y el efecto <b>no existe</b>.</span></div> <div class="panel"><b>El efecto se pierde en silencio</b><br/><span class="opacity-75 text-sm">Si el proceso cae entre el commit del ES y el handle del evento, el efecto secundario <b>desaparece</b>.</span></div> </div> <div class="mt-4 cite"> wolverinefx.net/guide/messaging/transports/local · /guide/runtime · Jeremy D. Miller, "Wolverine's Runtime Architecture". </div> <!-- Este es el argumento técnico FUERTE, no el del tenant. local:// no durable = no hay misma transacción ni garantía de entrega. Respaldado por las docs oficiales de Wolverine y los posts de Jeremy D. Miller. -->
El tenant es el humo, no el fuego: el contexto viaja en el envelope
<div class="opacity-80 mb-2">El contexto <b>no va en el payload</b> del evento: viaja en el <b>envelope y los headers</b> del mensaje de Wolverine. El broker los serializa y los <b>rehidrata</b> en el receptor; <code>local://</code> (in-memory) <b>no hidrata</b> el <code>IMessageContext.TenantId</code> — y ahí el resolver se queda sin contexto.</div>
{all|1-3|5-7}
// El contexto NO va en el payload: viaja en el ENVELOPE + headers de Wolverine.
bus.PublishAsync(evento, new DeliveryOptions { TenantId = tenantId }
    .WithHeader(TenancyHeaders.UserId, userId));

// El receptor lo lee del envelope que Wolverine hidrata desde el transporte:
var tenant = messageContext.TenantId;                                 // broker: ✓ rehidratado
var user   = messageContext.Envelope?.Headers[TenancyHeaders.UserId]; // local://: ✗ no llega
<div class="mt-4 panel border-teal-500"> Sobre un <b>broker</b>, el transporte serializa el envelope/headers y los rehidrata en el receptor. Sobre <code>local://</code> el <code>IMessageContext.TenantId</code> <b>no se hidrata</b> y el <code>ITenantResolver</code> queda sin contexto. </div> <!-- Nota para vos (no proyectar): el equipo ya observó que local:// NO hidrata IMessageContext.TenantId (documentado en el PR #21). El argumento conceptual primario sigue siendo la no-durabilidad y la semántica de consistencia — el tenant es el síntoma observable. Si alguien lo cuestiona, se cierra con un test: publicar un IPrivateEvent con DeliveryOptions.TenantId a una cola local y afirmar IMessageContext.TenantId en el receptor. -->
Lo que están mezclando bajo un solo mecanismo
Uso real	Qué es	Cómo debe resolverse
<span class="text-teal-400">Eventos de ES</span>	Estado	Van al event store. No se "publican para handlear".
<span class="text-amber-400">Misma decisión de negocio</span>	Efecto del mismo comando	Flujo explícito o domain event diferido a commit, mismo scope.
<span class="text-red-400">Reacción cross-cutting</span>	Otro proceso / otro BC	EDA real: consistencia eventual, outbox, async, idempotencia, tenant en el evento.
<div class="mt-5 panel"> El error: meter el <b>caso cross-cutting</b> (o un caso de "mismo comando" mal acotado) por el <b>mecanismo del primero</b>. </div>

La regla dura para el building block
<div class="space-y-3 mt-2"> <div class="panel border-teal-500"><b>1.</b> Eventos de ES → al event store. No se publican a una cola para handlear.</div> <div class="panel border-teal-500"><b>2.</b> Misma decisión de negocio → flujo explícito o domain event diferido a commit, en el <b>mismo scope</b>.</div> <div class="panel border-teal-500"><b>3.</b> Reacción cross-cutting → EDA real: outbox + async + idempotencia + <b>tenantId en el evento</b>.</div> <div class="panel border-red-500"><b>4.</b> Un handler de evento <b>nunca</b> ejecuta lógica de dominio que pueda ser rechazada. Si puede fallar/validar → es un comando, hazlo explícito.</div> </div> <div class="mt-4 panel border-amber-500"> <span class="text-amber-400 font-mono text-sm">Implicación para PR #21:</span> el validador no debería exigir "broker externo" para <b>todo</b> evento privado (eso volvería <i>overkill</i> los domain events in-process), sino <b>endpoint durable + contexto propagado</b> cuando el efecto cruza agregado o proceso. Así la regla #2 sigue siendo legal. </div> <div class="mt-4 opacity-70 text-sm"> Esto le da al equipo un patrón legítimo y claro para cada caso — y la frontera conceptual que faltaba. </div>
